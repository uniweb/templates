# Start Small, Ship Often

The hardest part of any project isn't the code — it's deciding what *not* to build yet. A small thing in someone's hands beats a big thing in your head.

## Why small wins

Shipping early changes the conversation. Instead of arguing about hypotheticals, you get to react to something real.

- Feedback arrives while it's still cheap to act on
- Scope creep has fewer places to hide
- Momentum compounds: each release makes the next one easier

## A simple rhythm

1. Pick the smallest slice that delivers value on its own
2. Build it end to end — not the prettiest layer of everything
3. Release it, watch how it's used, and let that pick the next slice

> Make it work, make it right, make it fast — in that order, and usually on different days.

The goal isn't to be sloppy. It's to learn in public, on a short loop, so the thing you eventually polish is the thing people actually wanted.
